# DukenAI

MVP прогноза спроса для пекарни и небольшого магазина. Загружает продажи из CSV, учитывает день недели, район, праздники и погоду, затем показывает план выпечки/закупки на день и неделю. Ничего не заказывает автоматически.

**Внешнего ИИ и платных API здесь нет.** Текстовая сводка составляется из результатов расчёта по шаблону (`mode: rules`). Ключи OpenAI и DeepSeek не нужны. Единственный внешний запрос — погода Open-Meteo по координатам выбранного города; продажи и названия товаров туда не передаются.

## Запуск

Нужны Node.js 22+ и npm. Из папки проекта:

```sh
npm ci
npm start
```

Откройте [http://localhost:3000](http://localhost:3000). Порт можно изменить переменной `PORT`. Для разработки есть `npm run dev`, для проверки — `npm test`.

Сайт сразу открывается с синтетическими данными: 90 дней, 15 товаров, 1 350 строк. Даты в режиме демо обновляются автоматически относительно текущего дня в Казахстане. Чтобы обновить файл `demo-sales.csv` на диске, выполните `npm run demo`.

## Демо за минуту

1. Нажмите «Использовать демоданные» или загрузите свой CSV.
2. Выберите город, район и дату. Нажмите «Рассчитать план».
3. Покажите спрос, количество к подготовке и график. Раскройте строку товара: видны база, поправки, запас и пригодный остаток.
4. Переключитесь на «Неделя» и покажите рекомендации по уценке.
5. Нажмите «Скачать план»: CSV выгружается в браузер, заказ поставщику не отправляется.

Фраза для защиты: «Коэффициенты пока заданы как гипотезы. На пилоте мы проверим их по реальным продажам и настроим правила».

## CSV

Кодировка UTF-8 или Windows-1251 (так Excel сохраняет «CSV» в русской Windows); разделитель — запятая или точка с запятой. Даты принимаются как `YYYY-MM-DD` или `DD.MM.YYYY`, пробелы в числах (`1 300`) допускаются. Обязательные колонки:

```csv
date,product,qty,price,stock,shelf_life_days
2026-10-24,Баурсаки,140,100,28,1
2026-10-24,Молоко,8,650,28,2
```

При использовании примера замените даты на фактические, не позднее сегодня.

| Колонка | Значение |
| --- | --- |
| `date` | Дата продаж: `YYYY-MM-DD` или `DD.MM.YYYY` |
| `product` | Название товара, 1–100 символов |
| `qty` | Продано за день, целое неотрицательное число |
| `price` | Розничная цена в тенге; может быть дробной |
| `stock` | Остаток, целое неотрицательное число |
| `shelf_life_days` | Сколько дней после даты строки остаток ещё можно продавать; `0` означает просрочку |

Одна строка на товар и дату. Повторы отклоняются. Дни без продаж добавляйте с `qty=0`: отсутствующая строка означает неизвестные продажи, а не нулевой спрос. Все количества измеряются в целых единицах товара — штуках, упаковках или порциях.

Для цены, остатка и срока годности используется последняя запись каждого товара. Срок годности отсчитывается от даты этой записи: если она старая, просроченный остаток не будет считаться пригодным. Если история старая, проверьте и обновите остаток и срок перед расчётом: программа не знает фактическое состояние полки. У разных партий одного товара в MVP нет отдельных записей.

Ограничения загрузки: 2 МБ, до 15 000 строк и 100 товаров. Неверный файл возвращает понятную ошибку, предыдущие данные сохраняются. В диалоге «Мои данные» доступен актуальный пример CSV.

## Расчёт

1. **База:** среднее последних четырёх одинаковых дней недели в пределах 56 дней. Если сопоставимых дней нет, берётся среднее последних 14 записей. При менее чем четырёх сопоставимых днях показывается предупреждение.
2. **Поправки:** коэффициенты перемножаются. Наурыз, Новый год, Курбан айт и 8 марта дают +30% для распознанных категорий муки, мяса и сладкого. 5-е и 20-е числа — +10%. Офисный район в выходные — −40%; университет — −25%, летом дополнительно −20%.
3. **Погода:** ниже +5°C чай получает +20%, мороженое −30%; от +28°C — чай −20%, мороженое +30%. Летом отдельно применяются −10% для чая и +10% для мороженого. Используется среднесуточная температура.
4. **Запас:** 5% для товара с оставшимся сроком до двух дней, 10% для остальных. Спрос округляется до целого, запас — вверх. План равен `max(0, прогноз + запас − пригодный остаток)`.
5. **Неделя:** семь дневных расчётов. Симуляция остатков всегда начинается с завтрашнего дня: если выбрана более поздняя дата, дни до неё тоже рассчитываются (продажи идут по прогнозу, выпечка — по плану), и остаток не считается нетронутым. Начальный остаток учитывается один раз; партии расходуются по ближайшему сроку годности, непроданный пригодный остаток переносится. Просроченные партии исключаются. Срок новых партий условно равен последнему сроку из CSV, минимум один день; для пилота нужны реальные сроки новых партий.
6. **Уценка:** остаток сравнивается с суммой прогнозируемых продаж до срока годности (считается от даты записи), максимум за 14 дней. При избытке предлагается скидка 20%, при оставшемся одном дне — 30%. Просроченный товар предлагается убрать с продажи. Уценка не гарантирует продажу.

Категории определяются по ключевым словам в названии товара. Это ограниченная демонстрационная классификация. Сумма «под риском списания» — розничная стоимость прогнозируемого избытка, **не** себестоимость потерь или обещанная экономия.

## API

Данные привязаны к cookie `dukenai_session`. При работе вне браузера сохраняйте и отправляйте cookie между запросами.

| Метод | Путь | Ответ / действие |
| --- | --- | --- |
| `GET` | `/api/health` | Проверка доступности |
| `GET` | `/api/config` | Даты, города, районы и метаданные набора |
| `POST` | `/api/upload` | Проверить CSV и заменить набор текущей сессии |
| `POST` | `/api/demo` | Вернуться к демоданным |
| `GET` | `/api/demo.csv` | Скачать актуальные 90 дней демопродаж |
| `GET` | `/api/forecast?date=YYYY-MM-DD&district=residential&city=almaty` | Дневной и недельный планы, история, советы, сводка |
| `GET` | `/api/tips` | Рекомендации по остаткам на сегодня |
| `GET` | `/api/summary` | Текстовая сводка, `mode: rules` |

`/api/tips` и `/api/summary` принимают те же параметры, что `/api/forecast`. Если параметры не указаны: завтра, жилой район, Алматы.

- `district`: `residential`, `office`, `university`.
- `city`: `almaty`, `astana`, `kyzylorda`.
- `date`: от завтра до девяти дней вперёд включительно. Недельный план может доходить до 15-го дня от сегодня.

Загрузка использует **тело запроса с CSV**, а не `multipart/form-data`:

```http
POST /api/upload
Content-Type: text/csv; charset=utf-8

date,product,qty,price,stock,shelf_life_days
2026-10-24,Баурсаки,140,100,28,1
```

Также принимаются сырые байты файла с `Content-Type: application/octet-stream` (кодировка UTF-8 или Windows-1251 определяется автоматически; так загружает сайт) и JSON: `{"csv":"date,product,qty,price,stock,shelf_life_days\n..."}` с `Content-Type: application/json`.

## Render

1. Создайте репозиторий GitHub и загрузите содержимое этой папки, включая `package-lock.json`. `node_modules` и `.env` не загружайте.
2. В Render выберите **New → Web Service**, подключите репозиторий.
3. Укажите **Build Command:** `npm ci`, **Start Command:** `npm start`, **Health Check Path:** `/api/health`.
4. Используйте Node.js 24 и `NODE_ENV=production`. `PORT` задаёт Render. Ключи ИИ не добавляйте: они не используются.
5. Альтернатива ручной настройке — создать Blueprint из включённого `render.yaml`. В нём выбран план `free`; доступность и условия тарифа проверяйте в аккаунте Render.

Официальная инструкция: [Deploy a Node Express App on Render](https://render.com/docs/deploy-node-express-app).

## Хранение и ограничения MVP

- CSV хранится только в памяти одного процесса сервера; на диск и стороннему ИИ не отправляется. Cookie содержит случайный идентификатор сессии, а не продажи.
- Сессия рассчитана на два часа бездействия. При перезапуске или повторном развёртывании сервера загруженные данные исчезают. Сохраните исходный CSV у себя.
- Загруженные CSV ограничены 100 сессиями и 150 000 строками суммарно. Сессии без загрузки не ограничивают новых посетителей: при большом числе удаляются самые давние из них. На одну сессию разрешено до 60 API-запросов в минуту.
- Нет аккаунтов, базы данных, долговременного хранения и общей сессии между несколькими экземплярами сервера. Для реального запуска потребуются авторизация, постоянное хранилище и отдельная модель остатков по партиям.
- Если выбрана дата позже завтра, продажи в промежуточные дни берутся из прогноза, а выпечка — из плана; фактические промежуточные продажи неизвестны.
- График показывает последние 30 календарных дней до сегодня; старые CSV могут давать пропуски. Продажи при отсутствии товара способны занижать оценку реального спроса.
- Погода запрашивается у Open-Meteo с тайм-аутом 4 секунды и кешируется на 30 минут. При недоступности расчёт продолжается без погодного коэффициента. Для проверки этого режима задайте `WEATHER_DISABLED=1`.
- Праздничные даты и поправки не моделируют перенесённые рабочие дни. Курбан айт внесён только на 2026 год; для других лет нужно обновить `holidays.js`. Это не производственный календарь.
- Коэффициенты, запас и скидки — гипотезы. Точность на реальных данных пока не измерена.

Интерфейс работает без внешних библиотек графиков и шрифтов. Проверки запускаются командой `npm test` и включают разбор CSV, календарные/погодные поправки, недельный учёт остатков, уценку и изоляцию сессий API.

Справочные источники: [Open-Meteo API](https://open-meteo.com/en/docs), [праздничные дни Казахстана — eGov](https://egov.kz/cms/ru/articles/holidays-calend).
